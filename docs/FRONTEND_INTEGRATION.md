# Frontend integration package

## Status

This package is a static, deterministic demonstration generated by
`scripts/export_demo.py` from fictional inputs using the existing Python
parsers, detector, and privacy engine. It makes no cloud calls. The repository
does not currently contain a React/Vite application, Firebase configuration,
or JavaScript implementation of these engines; this document describes a
future integration without creating or changing a frontend.

Regenerate and validate the files from the repository root:

```text
python scripts/export_demo.py
python -m unittest discover -s tests -v
```

The export uses only in-code synthetic events and checked-in contracts. It
does not read `data/raw/`, `data/reference/`, or processed LogHub outputs.
Example usernames, hostnames, and addresses are fictional; IPs are reserved
documentation addresses. The privacy example contains a deliberately
nonfunctional token marker. Never replace these with operational data in
files intended for public distribution.

## Exported files

| File | Structure and intended use |
| --- | --- |
| `demo/events.json` | Array of normalized event objects conforming to `contracts/event-v1.json`. Fictional detector inputs; contains no scenario labels. |
| `demo/alerts.json` | Array of local Python detector alerts conforming to `contracts/alert-v1.json`. `evidence_event_ids` point into `events.json`. |
| `demo/sanitized-events.json` | The same fictional events sanitized with one fixed demo investigation context. Use to demonstrate pseudonymization and credential redaction. |
| `demo/sanitized-alerts.json` | Detector alerts sanitized locally. This remains a demo output, not proof of anonymity. |
| `demo/cloud-payload-examples.json` | Valid minimized payload examples plus rejection outcomes. These are examples only and never authorize or initiate a request. |
| `demo/dashboard-summary.json` | Counts for a simple overview. It contains no ground-truth labels. |
| `demo/annotations.json` | Separate synthetic scenario labels keyed by event ID. Test/evaluation sidecar only; do not pass it to the detector or use it as a user-facing security verdict. |
| `demo/validation-report.json` | Export-time checks and counts. |
| `tests/fixtures/integration-v1.json` | Versioned golden inputs and expected parser, detection, privacy, and cloud-validation results for future cross-runtime tests. |

Events share the normalized top-level fields `event_id`, `source`,
`timestamp`, `event_type`, `username`, `source_ip`, `status`, `message`, and
`metadata`. Alerts share the detector's 15-field alert shape. The cloud
payload is narrower: `schema_version`, `rule_id`, `severity`, `category`,
`source`, pseudonymized `entities`, `event_count`, minimized `relative_time`,
and `evidence_summary`. See the corresponding versioned contracts under
`contracts/`.

The synthetic scenarios demonstrate normal authentication, repeated
failures, a success after failures, password-spraying indicators, contextual
privilege-escalation evidence, and privacy sanitization. The detector remains
deterministic. A rule match is evidence for review, not a confirmed attack.

## Import and display from React

Once a frontend exists, a Vite component can import the static JSON directly.
For example, from a root-level `src/App.jsx`:

```jsx
import events from "../demo/events.json";
import alerts from "../demo/alerts.json";
import summary from "../demo/dashboard-summary.json";

const eventsById = new Map(events.map((event) => [event.event_id, event]));

export function DemoDashboard() {
  return (
    <main>
      <p>{summary.event_count} fictional events</p>
      <p>{summary.security_alert_count} security alerts</p>
      <ul>
        {alerts.map((alert) => (
          <li key={alert.alert_id}>
            <strong>{alert.severity}: {alert.rule_name}</strong>
            <p>{alert.description}</p>
            <ul>
              {alert.evidence_event_ids.map((id) => {
                const event = eventsById.get(id);
                return (
                  <li key={id}>
                    {id}: {event ? event.message : "Evidence unavailable"}
                  </li>
                );
              })}
            </ul>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

Render `category` distinctly: `security` alerts are separate from
`operational_anomaly` alerts such as R07. Show the rule, severity, description,
and evidence references; do not imply that a synthetic label or an
unlabeled-LogHub pattern is a confirmed attack. Do not import
`demo/annotations.json` into the detector or display it as a real-world
judgment.

To demonstrate privacy, display a fictional event alongside its corresponding
entry in `sanitized-events.json`. Explain which identifiers were replaced and
that credentials are redacted; do not imply the result is guaranteed
anonymous. The demo pseudonym context is fixed only for reproducibility.

## Consent and Gemini Cloud boundary

`demo/cloud-payload-examples.json` is display/test data. **It is not
authorization to call Gemini or any other cloud service.** Any future request
requires an explicit user action and consent for that particular analysis.
The only permissible request body is a newly built and validated payload
conforming to `contracts/cloud-payload-v1.json`:

- Rule identifier, severity, category, and source.
- Pseudonymized source IP/account aliases only.
- Event count.
- Relative time with a recognized basis, when available.
- Sanitized evidence summary.

Never submit raw events, raw messages, complete alerts, alert/evidence IDs,
timestamps, metadata, credentials, annotations, or pseudonym maps. Do not put
raw logs into a chat history, Firestore, analytics, crash reporting, or remote
debug logs. If consent is absent, sanitization fails, validation rejects, or a
cloud request fails, stop and show a local error. **Do not retry through an
automatic cloud fallback with raw logs or an unrestricted object.**

The Python `authorized=True` parameter is a fail-closed API guard, not a
replacement for frontend consent. No Firebase/Gemini transport or fallback
exists in this repository yet.

## Precomputed versus dynamic behavior

- **Precomputed for this demo:** parsing examples, normalized events, rule
  alerts, pseudonymized outputs, accepted payload examples, rejection
  decisions, and dashboard counts.
- **Not dynamically run by React:** Python parsing, timestamp correlation,
  detection rules, PII scanning, pseudonym generation, and payload validation.
  Importing JSON only displays the Python-produced reference outputs.
- **Future browser implementation:** process selected files locally, port the
  contracts and algorithms to JavaScript, and compare outputs with
  `tests/fixtures/integration-v1.json` before enabling live analysis.
- **Future local Python option:** a loopback-only service could reuse the
  existing engines, but would need origin checks, request limits, local
  service protections, and a tested browser-to-service boundary.

Keep raw-file processing local. Until dynamic parity, consent UI, and the
cloud boundary are independently tested, use only these synthetic files in
the frontend demo.

## Golden fixture use

The fixture bundle contains raw fictional parser lines with Python parser
outputs, label-free detector inputs with expected alerts, a privacy input and
sanitized output, and accepted/rejected cloud payload decisions. Future
JavaScript tests should compare parsed fields, rule/category/severity,
evidence IDs, sanitization results under the fixed test context, and payload
accept/reject decisions. Keep annotation labels separate from these
detector-input objects.
