# Privacy protection engine

## Scope and data flow

The local Python modules in `privacy/` detect and sanitize common sensitive
entities in normalized events, alerts, and nested JSON-compatible values. They
do not modify their inputs, persist pseudonym maps, or make network requests.
No cloud API is called in this phase.

Typical local use:

```python
from privacy import Pseudonymizer, sanitize_event

context = Pseudonymizer()
safe_event = sanitize_event(local_event, context)
```

Keep one `Pseudonymizer` instance for a single investigation to preserve
relationships. Create a new instance for a different investigation. Its
context tag is randomly generated by default; maps exist only in process
memory. Do not log, serialize, or send the internal mapping. Pseudonymized
values are linkable within their investigation and are **not guaranteed
anonymous**.

## Supported information

| Information | Detection approach | Transformation |
| --- | --- | --- |
| IPv4 and IPv6 | Validated address candidates; recognized source/client IP fields | `IP_<context>_NNN` |
| Usernames and account IDs | Username/account field names and recognizable login-message contexts | `USER_<context>_NNN` |
| Hostnames | Host fields, `host=`/`hostname=` context, and hostname-shaped names | `HOST_<context>_NNN` |
| Email addresses | Address-shaped text and email fields | `EMAIL_<context>_NNN` |
| Phone numbers | Delimited phone-number patterns and phone fields | `PHONE_<context>_NNN` |
| MAC addresses | Delimited six-octet patterns and MAC fields | `MAC_<context>_NNN` |
| Sensitive file paths | User-home, private, and selected system paths; path fields | `PATH_<context>_NNN` |
| Passwords and passphrases | Credential field names and explicit key/value patterns | `[REDACTED_PASSWORD]` |
| API keys and access tokens | Explicit key/value patterns and recognizable provider token prefixes | `[REDACTED_SECRET]` |
| Authorization headers | Bearer, Basic, and Token authorization patterns/fields | `[REDACTED_AUTHORIZATION]` |
| Session IDs and cookies | Session/cookie field names and explicit assignments | `[REDACTED_SESSION]` |
| Private keys and other secrets | Private-key blocks, secret/credential fields, and selected credential patterns | Type-appropriate full redaction |

Detection is field-aware: arbitrary numeric values, process IDs, counters,
versions, and durations are not redacted merely because they contain digits.
Known identifier fields can still be pseudonymized even when their value is
not recognizable from free text.

## Modules and behavior

- `privacy/pii_detector.py` returns typed findings with local-only source
  locations. Findings and exceptions do not print their matched values.
- `privacy/anonymizer.py` maintains per-context entity aliases and fully
  redacts credential values.
- `privacy/privacy_filter.py` sanitizes nested values, normalized events, and
  the existing cybersecurity alert schema into new objects. Malformed event
  schemas and non-JSON values fail explicitly.
- `privacy/cloud_payload_builder.py` constructs a minimized allowlisted
  payload only after explicit authorization, then validates its schema and
  scans for residual sensitive information.

An input such as a fictional event with username `analyst-01`, source IP
`192.0.2.25`, and message `Failed login for analyst-01 from 192.0.2.25` can
become:

```json
{
  "username": "USER_A1B2C3D4_001",
  "source_ip": "IP_A1B2C3D4_001",
  "message": "Failed login for USER_A1B2C3D4_001 from IP_A1B2C3D4_001"
}
```

The example context tag is fixed for documentation only; production contexts
use a random tag. Repeated entities remain linkable inside one context, while
different contexts produce different aliases. Secrets are never pseudonymized
because preserving them would retain the secret itself.

Credential values are fully redacted, for example:

```json
{"password": "Fictional-Only-Value", "api_key": "FAKE_API_KEY_001"}
```

becomes:

```json
{"password": "[REDACTED_PASSWORD]", "api_key": "[REDACTED_SECRET]"}
```

## Guarantees provided by these local APIs

- Sanitizers return new JSON structures and leave supplied event/alert objects
  unchanged.
- Credential fields and recognized credential patterns are replaced rather
  than reversibly pseudonymized.
- The cloud builder requires an explicit authorization flag, selects only its
  fixed schema, pseudonymizes supported entities, and rejects detected
  residual sensitive content.
- No network request or automatic cloud fallback exists in this phase.

## Limitations

The detector uses regular expressions, field names, and IP address parsing.
It can miss obfuscated, encoded, novel, or context-dependent values; patterns
can also flag unusual but benign text. Short usernames in free text are
especially ambiguous. Review detection policy and test it against the actual
application schema before relying on it. Do not treat a zero-leakage synthetic
result as a privacy guarantee.

The raw dataset and generated test data remain local and Git-ignored. Do not
send raw logs through automatic cloud fallback; cloud analysis must consume
only a validated payload built after explicit user authorization.
